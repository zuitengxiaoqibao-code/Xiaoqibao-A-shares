# A 股全市场日线同步设计

日期：2026-07-27

## 目标

把现有“用户点一只、同步一只”的日线流程升级为后台全市场任务，为首次涨停、市场情绪、候选评分和回测提供统一日线底座。系统必须使用真实来源、支持断点续传、暴露覆盖率，并且不能因为全量同步阻塞前台页面。

当前基线：证券目录已有 5,980 只 A 股，日线库只有 13 只股票，其中 12 只具备至少 250 个交易日。现有 mootdx 适配器只配置 5 个节点，TCP 可连接但实测均返回空行情；现有接口只能同步单只股票。

## 范围

- 同步证券目录中的全部有效 A 股，包括沪市、深市和北交所。
- 首次回填每只股票最近 300 个交易日；满足首次涨停所需的 250 日最低历史，并为周线、月线位置判断留出余量。
- 日常盘后只补缺失交易日，不重复写入整段历史。
- 首次涨停规则继续只处理其允许的市场范围；日线底座本身不删除北交所数据，方便以后扩展。
- 不在本期实现分钟线全市场回填、自动交易、券商下单或收益承诺。

## 方案选择

采用“通达信主源 + 百度回退”的方案。

通达信节点池由静态可信节点、mootdx 可发现节点和最近成功节点组成。节点不能只做 TCP 握手判断，必须用真实日线请求验证；返回空数据同样视为失败并切换节点。某只股票在全部通达信节点失败后才进入百度回退，避免把 HTTP 回退源当作高频主源。

不采用纯百度方案，因为 5,980 只股票的首次回填请求量大，速度和限流风险更高。不依赖本机通达信客户端文件，因为安装路径、复权方式和本地下载完整度不可控。

## 架构

### 1. 日线同步任务仓库

新增独立 SQLite 仓库，保存：

- 任务编号、模式（首次回填或盘后增量）、目标交易日、创建时间和状态；
- 证券总数、待处理数、成功数、失败数、跳过数和最近更新时间；
- 每只股票的状态、尝试次数、最终来源、写入行数和安全错误码；
- 当前批次游标和取消标记。

任务状态必须可在进程重启后恢复。相同目标交易日的增量任务具有幂等键，重复触发不会创建并行重复任务。

### 2. 通达信节点管理

在现有 `TdxFailoverClient` 上增加节点健康缓存：

- 最近成功节点优先；
- TCP 不可达、创建客户端失败、协议错误和空响应分别记录；
- 用固定、有效的沪深样本请求验证节点是否真正提供行情；
- 连续失败触发短期熔断，熔断期后允许重新探测；
- 不把底层地址、堆栈或敏感环境信息展示给新手页面。

节点健康只影响选择顺序，不改变收到的行情内容。

### 3. 全市场同步服务

同步服务从 `AShareInstrumentDirectory.active_symbols()` 取得稳定快照，并按代码排序分批处理。

- 首次回填：对历史不足 300 日的股票请求最近 300 日；已有足够历史则跳过。
- 盘后增量：读取各股票最新交易日，只请求小窗口并仅写入更新日期之后的数据。
- 单只股票先走通达信，全部节点失败后走百度。
- 默认最多 2 个通达信工作线程；百度回退串行限速，避免放大外部服务压力。
- 每完成一只股票立即提交任务进度，每完成一个小批次提交日线数据；进程中断最多重做当前股票。
- 单只失败不终止整个任务。达到全局失败阈值时暂停任务并报告数据源不可用，避免在主源整体故障时对 5,980 只股票反复空请求。

日线写入前按股票和交易日过滤已存在记录。正常增量不会重复追加相同历史，显式修复任务才允许写入同日新修订。

### 4. 调度顺序

- 首次回填由用户在数据设置页启动，后台持续运行并可在重启后继续。
- 每个交易日收盘后创建增量任务。
- 首次涨停扫描只使用最近一个“同步完成且覆盖率达标”的交易日。
- 增量任务未完成时保留上一交易日结果，并明确标注“日线同步中”，不能把不完整截面显示成全市场结论。

### 5. API 与界面

新增接口：

- 启动首次回填；
- 启动或恢复盘后增量；
- 查询当前任务进度；
- 查询日线覆盖摘要；
- 暂停当前任务。

数据设置页展示总股票数、250 日达标数、最新完整交易日覆盖数、任务进度、通达信/百度成功数和失败数。首次涨停页展示本次扫描覆盖数与全市场基数；覆盖不完整时用醒目提示说明结果只是部分市场，不能显示“全市场已扫描”。

## 数据质量和错误处理

- 校验股票代码、交易日期、OHLC 关系、成交量、成交额和严格递增日期。
- 单次返回只要出现非法行，整只股票该次结果不入库并切换来源。
- 新上市股票不足 250 日属于“历史自然不足”，不算数据源失败，也不能进入需 250 日的首次涨停筛选。
- 停牌股票允许目标日无新 K 线，但必须保留上次有效日期。
- 退市或已不在活动目录的股票不参与新任务，历史数据不删除。
- 页面只展示已验证覆盖率和安全错误分类，不把缺失值补成零，不生成虚构日线。

## 性能与运维

- 全量回填在后台线程运行，API 请求只负责创建任务并立即返回。
- DuckDB 写入按小批次串行提交，避免多工作线程同时写文件。
- 进度更新节流，避免每根 K 线写一次 SQLite。
- 任务可安全暂停；应用退出时停止领取新股票，正在处理的单只完成或超时后退出。
- 日线库和任务库继续纳入现有备份流程。

## 测试与验收

- 节点测试：TCP 可达但空响应时切换；最近成功节点优先；熔断后可恢复。
- 服务测试：首次回填、增量过滤、百度回退、自然不足、单只失败继续、全局失败暂停。
- 仓库测试：任务幂等、进度原子更新、重启续传、暂停和完成状态。
- 路由测试：创建任务立即返回、进度和覆盖摘要字段稳定、错误信息不泄漏内部细节。
- 调度测试：盘后先同步、覆盖达标后再扫描首次涨停。
- 界面测试：显示真实覆盖分母；部分覆盖时不得出现全市场完成文案。
- 集成冒烟：使用少量沪深股票验证通达信真实回填；通达信不可用时验证百度回退，不将联网冒烟作为离线 CI 的硬依赖。
- 完成门禁：后端和前端全量测试、生产构建、严格 UTF-8/乱码扫描与差异检查通过。

## 验收标准

1. 用户无需逐只点击即可创建全市场回填任务。
2. 任务中断并重启 API 后能够从未完成股票继续。
3. 日线库覆盖摘要能准确区分目录总数、300 日回填完成数、250 日可分析数和最新交易日覆盖数。
4. 通达信节点返回空数据时自动切换，全部失败才使用百度回退。
5. 首次涨停页面不再把 12 只股票的结果呈现成全市场结果。
6. 任何缺失或失败都保留真实状态，不伪造行情或候选。
