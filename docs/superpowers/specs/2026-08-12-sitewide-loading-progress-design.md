# 全站加载进度连续反馈设计

日期：2026-08-12

## 问题

公司研究和个股观察调用本地 API 时，后端会先完成查询与计算，再返回响应头。现有前端只在请求发起时报告 `1%`，因此等待期间长时间没有变化；响应到达后，接收和解析通常很快，进度便直接跳到 `100%`。

## 设计

- 共享请求层在等待响应头期间提供连续的阶段估算进度，从 `1%` 平滑趋近安全上限 `45%`，并显示真实已等待时间。
- 阶段估算必须明确标注“阶段估算”，不得声称是后端真实完成比例。
- 响应头到达后切换到数据接收阶段：存在 `Content-Length` 时按真实字节比例推进；不存在时公开已接收字节，并以保守估算推进。
- 数据完整接收后进入 `96%` 校验与解析阶段；只有 JSON 成功解析才进入 `100%`。
- 进度轨道增加克制的流光运动，即使百分比在短时间内不变化，也能明确表示任务仍在运行；尊重 `prefers-reduced-motion`。
- 公司研究和个股观察通过共享 `fetchJsonWithProgress` 与 `DailyRefreshStatus` 一次修复。
- 信息总览继续使用真实阶段节点，量化候选继续使用后端处理数量，不改写已有更可信的进度来源。

## 失败与取消

- 请求失败时停止计时器，保留失败前最后进度、阶段和原因。
- 请求取消时停止计时器，不产生完成事件。
- 进度不得倒退，不得在解析成功前到达 `100%`。

## 验证

- 使用虚拟计时器证明响应头尚未到达时进度会从 `1%` 连续上升且不超过 `45%`。
- 验证响应到达后进入接收和解析阶段，最终完成为 `100%`。
- 验证失败和取消会清理计时器。
- 验证共享状态组件展示进度可信度和持续运动样式。
- 完成 Web 全量测试、生产构建、编码扫描、便携 EXE 重建和真实发布 smoke。
